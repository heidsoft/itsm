# ActionFlow 引擎：设计评估与暂缓建议

> 结论先行：**不建议在本阶段实施**。理由不是「做不出来」，而是它会与现有
> 三条执行语义竞争，把「副作用最终由谁执行」这一已经收口的问题重新打开。
>
> 本文档是该判断的完整依据与「如果将来要做，必须怎么做」的边界设计。
>
> 对应《Agent 控制面差距报告》（`output/agent-control-plane-gap-2026-11-21.md`）
> 原计划 P1 第二项。日期 2026-11-21，基线 `HEAD=ac01a2c8b`。

---

## 1. 问题：ActionFlow 想解决什么

差距报告把 ActionFlow 列为 P1，原始诉求是「一次 Agent 决策可能涉及多个
相继的副作用操作，需要把它们表达成一个可审批、可回放、可补偿的单元」。

这个诉求是真实的。当前 `create_ticket` + `link_ticket_ci` + `update_ticket`
三个调用是**三次独立审批**，审批人看到三条孤立待办，无法感知「这三条是同一
决策」。差距报告据此提出「ActionFlow 引擎」。

## 2. 现状：已有三条执行语义，各自都有 exactly-once 锚点

在提出第四条之前，必须先把现有三条看清楚。

| 执行路径 | 谁判定 | 谁执行副作用 | exactly-once 锚点 |
|:--|:--|:--|:--|
| **HTTP 直调** `POST /agent/tools/execute` | `ai.Service.evaluateToolCall` | 同步在请求内执行（只读）或建待审批行（写） | 无（单次请求） |
| **chat / investigate 循环** | 同上（同一函数） | 只读立即执行；写工具建待审批行 | 无（单次请求） |
| **MCP / Skill 通道** | 同上（同一函数） | 同上 | 无 |
| **审批后执行** `DecideToolInvocation` → `commandbus` | 审批时不再判定（沿用排队时结论 + 复核接口可查差异） | `ToolExecutor` 从 `operational_commands` **CAS 领取** | `operational_commands` 状态机 + `run_id` + `invocation_id` |
| **BPMN ServiceTask** | 流程引擎 | 由 BPMN 桥接调用业务 service | 完成事务内锚点 |

关键事实：**所有副作用都收敛在 `commandbus` outbox**（写工具），或收敛在
BPMN ServiceTask（流程内）。这两处都有「领取即改状态」的 CAS 语义，
重复触发不会重复执行。

也就是说：**「谁来执行副作用」这个问题在本项目已经收口了**。这不是自然形成
的，而是有意的架构决定——`ExecuteTool` 的注释明确写了它「只判定并建
invocation，副作用由 `ToolExecutor` 从 outbox 领取」。

## 3. 为什么第四条并行流危险

引入 ActionFlow 引擎意味着新增一个「按步骤顺序驱动多个工具调用」的执行者。
它有四种可能的落地方式，每种都有具体问题：

### 方式 A：ActionFlow 自己调 `ExecuteTool` 逐步骤执行

- **问题**：每个步骤各自建一条待审批行，审批人仍然看到 N 条孤立待办。
  ActionFlow 只是把 N 次调用包在一个循环里，**没有解决原始诉求**
  （「让审批人看到这是一个整体」）。
- 更糟：如果 ActionFlow 在审批通过后自己执行，它就绕过了 `ToolExecutor`
  的 CAS 领取——同一 flow 被重复触发会重复执行副作用。

### 方式 B：ActionFlow 建一个「复合 invocation」

- **问题**：`tool_invocations` 的每一行当前对应**一个** `tool_name` +
  一份 `arguments`。复合行要表达「多个工具、多个参数集、有顺序、有依赖」，
  等于把 schema 从「一次调用」改成「一次计划」。这会导致：
  - `ListToolInvocations` 的审批待办语义分裂（有些行是一次调用、有些是一次计划）；
  - `run_id` 归属混乱（复合行与子调用谁持有 run_id）；
  - `policy_version` 语义破产——一次计划里每个步骤的判定输入不同，指纹无法
    用一个值表达。而「策略版本 = 判定输入指纹」是本项目审计可回放的核心等式，
    破坏它等于让整个 P0 审计工作失效。
- 这是**破坏既有不变量**的代价，不是新增能力的代价。

### 方式 C：ActionFlow 建 BPMN 流程

- 已经是现成的、正确的位置。BPMN 天然表达「有顺序、有网关、有 ServiceTask」，
  且 ServiceTask 已有 exactly-once 锚点（完成事务内）。
- **问题**：Agent 决策产生的 flow 是**动态的**（步骤由 LLM 决定，事前不存在
  流程定义）。BPMN 需要先有流程定义（deploy 后实例化），而 Agent 场景是
  「先有决策、后有步骤」。要为每个决策动态 deploy 一个 BPMN 流程，会让
  流程定义表膨胀且无法治理（每个 Agent 会话一条定义）。
- 折中方案（见 §4）是「预置若干流程模板，Agent 只能选择模板不能自造步骤」。

### 方式 D：ActionFlow 作为「审批分组的展示层」，不碰执行

- 这是**唯一不引入竞争**的方案。ActionFlow 只表达「这几条 invocation 属于
  同一决策」，用于：
  - 审批页把同组待办折叠成一个卡片（一次批准 = 逐条批准）；
  - 审计回放按组聚合展示。
- 执行仍走既有路径（每条 invocation 各自入 outbox、各自 CAS 领取）。
- **代价**：它不提供「补偿」（步骤 3 失败要回滚步骤 1、2）。但这个代价可以
  接受：分布式补偿本就是本项目未承诺的能力，而假装提供补偿（实际只是
  「失败后不再执行后续步骤」）比明确不提供更危险。

## 4. 建议：本阶段只做方式 D 的最小形态，且不作为 P1

**判断：方式 D 是正确方向，但它不是「ActionFlow 引擎」，而是「决策分组」。**
两者在实现上差一个数量级：

| 维度 | ActionFlow 引擎 | 决策分组（方式 D） |
|:--|:--|:--|
| 新增执行路径 | 是（第四条并行流） | 否（复用既有 outbox） |
| 是否需改 schema | 是（复合 invocation 或 flow 表） | 否（`tool_invocations` 已有 `run_id`） |
| 是否需改判定层 | 是（每步判定 or 复合判定） | 否（每步照常判定） |
| 是否破坏 `policy_version` 等式 | 是（复合行无法表达） | 否 |
| 补偿能力 | 声称有（实际不可靠） | 明确不提供 |

**关键发现：`run_id` 已经是「同一决策」的自然载体。** 本批（2026-11-21）
落地的 `run_id` 语义就是「跨请求的逻辑轮次」——同一次 Agent 决策产生的
所有工具调用共享同一个 `run_id`。已有的读面 `GET /agent/runs/{runId}/invocations`
就是「这一轮做了什么」的唯一查询。

因此「决策分组」**不需要新表、不需要新端点**，只需要：
1. 审批页按 `run_id` 折叠同组待办（前端改动）；
2. 批准时逐条调用既有 `POST /tools/{id}/approve`（不改后端语义）。

第 2 点有个诚实性问题必须先想清楚：**「整组批准」是假的一段事务。**
逐条批准是 N 次独立事务，中间失败会留下「批了一半」的组（第 1、2 条批了、
第 3 条失败）。这比「不提供整组批准」更危险——审批人以为整组批了，实际没有。

若要做「整组批准」，必须回答：第 3 条失败时第 1、2 条已入 outbox 怎么办？
可选答案：
- (a) 明确告知「已批准的 2 条不会回滚，第 3 条请重新审批」——诚实但用户体验差；
- (b) 引入两阶段提交（预批准 → 全部成功后集体放行）——需要新的状态机，
  会让 `DecideToolInvocation` 的 CAS 语义复杂化，且「预批准」态在界面上
  与「已批准」极易混淆。

**本阶段建议：不做整组批准，只做折叠展示。** 理由：折叠展示零风险地解决了
「审批人不知道这几条同属一个决策」的问题，而整组批准引入了本项目当前没有
能力诚实处理的分布式一致性问题。

## 5. 如果将来要做真正的 ActionFlow 引擎，必须满足的边界

记录下来，避免将来重新发明。

1. **执行语义必须唯一**：ActionFlow 不得自己执行副作用。它只能产生
   `operational_commands`（复用 `ToolExecutor` 的 CAS 领取），或产生 BPMN
   ServiceTask 实例（复用流程锚点）。任何「ActionFlow 内部直接调工具
   executor」的实现都违反本约束。
2. **判定仍走 `evaluateToolCall` 单一源**：每个步骤独立判定，用各自的
   工具名与参数。不得为 flow 发明「复合判定」——复合判定会与单步判定
   形成第二个判定点。
3. **`policy_version` 必须按步骤落**：复合行无法表达「每个步骤的判定输入」，
   因此存储层必须保持「一行一次调用」。flow 的身份由 `flow_id`（或复用
   `run_id`）表达，而不是把多个调用压成一行。
4. **补偿必须诚实**：要么不提供（明确文档化），要么用 outbox 的反向命令
   （`compensate` 类型的 command）实现，且必须在审计里可区分「因为失败而
   补偿」与「因为人工要求而撤销」。不得用「失败后不再执行后续步骤」冒充回滚。
5. **静态步骤优于动态步骤**：Agent 可选预置模板（如「建单→关联CI→挂KB」），
   不允许自造任意步骤序列。动态步骤序列无法治理（权限组合、审批人数、
   风险累积都无法预先评估）。

## 6. 现阶段应当做的事（替代 ActionFlow）

按优先级：

1. **审批页按 `run_id` 折叠同组待办**（展示层，零风险，解决主要诉求）；
2. **审计回放按 `run_id` 聚合已有读面**（`GET /agent/runs/{runId}/invocations`
   已存在，只需前端消费）；
3. **控制面聚合读面已在本批完成**，它让「同一时刻的队列/策略/可见面」
   可被一次查看——这是运维判断「策略改了生效没有」的前置条件。

这三项都不引入新的执行路径，且都直接服务于「完整业务闭环」的目标。

## 7. 未解决的问题（明确记录）

- 跨步骤的**风险累积**没有建模：`create_ticket`（中风险）+ `delete_ci`
  （高风险）作为一次 flow，当前按各自风险独立审批。是否应取最高风险？
  这需要产品决策，不属于引擎能力。
- 跨步骤的**权限交集**没有建模：如果 Agent 有 `ticket:write` 但无
  `ci:delete`，flow 在第 2 步被拒，第 1 步已执行。当前没有任何机制
  在 flow 开始前做「权限预检」。这是方式 A/B 都会遇到的真问题，
  也是它们需要「补偿」的根本原因。
