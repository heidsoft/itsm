## 0. 执行摘要

### 0.1 战略结论

CloudMesh 不应定位为又一个通用 AI Agent
Builder，也不应试图在早期替代企业全部 ITSM、ITOM、CMDB、RPA
或大模型平台。建议将 `heidsoft/itsm` 定位为：

> **面向企业 IT 服务团队、MSP 与 NOC 的 AI-Native IT Service &
> Operations 平台：以 ITSM 业务闭环为入口，以 Agent
> 执行能力为增量，以权限、审计、可靠执行和集成为企业级差异化。**

商业路径采用：

**开源建立信任与分发 → 垂直场景获得用户 → 付费 PoC 验证 ROI →
专业版/企业版授权 → 私有化交付与年度支持 → AgentOps / Governance
增购。**

产品策略的核心不是"功能越多越好"，而是先把一个业务闭环做得可靠、可部署、可验证、可收费，再把通用能力沉淀为平台。

### 0.2 当前优先级

  优先级   战略主题                  目标
  -------- ------------------------- ----------------------------------------
  P0       产品稳定性与架构收敛      用户能稳定使用，开发者能安全迭代
  P0       ITSM 核心业务闭环         工单、事件、客户、资产、知识和流程可用
  P0       MSP/NOC 场景适配          满足服务商、多客户、多分部和工程师协作
  P1       AI 邮件转工单             建立首个可演示、可收费的 AI 工作流
  P1       Agent 受控执行            工具权限、审批、幂等、审计、失败恢复
  P1       开源项目包装              文档、安装、Demo、Roadmap、Issue 规范
  P2       AgentOps / Governance     从垂直应用扩展为可复用执行治理能力
  P2       FinOps / 更多 ITOM 场景   在客户需求和渠道成熟后扩展

### 0.3 三条不可偏离的原则

1.  **客户问题优先于技术热点。** 不为"支持某个 Agent
    框架"而开发功能；只有客户工作流、交付效率或产品差异化需要时才引入。
2.  **生产可靠性优先于自治程度。** 任何会修改生产系统状态的 Agent
    操作，都必须经过身份、授权、策略、审批或明确的自动执行规则，并具备审计和恢复设计。
3.  **标准产品优先于项目定制。**
    客户专属需求应通过配置、Connector、Skill、扩展点或独立付费项目实现，不得持续污染核心产品。

## 1. 产品现状、已知背景与事实边界

本节汇总已知项目背景，作为战略规划输入。它不是对当前 GitHub
主分支的实时代码审计；执行研发任务前，应重新核对仓库、Issue、CI
和当前实现。

### 1.1 已知产品背景

-   项目仓库：`https://github.com/heidsoft/itsm`
-   产品品牌与业务方向：CloudMesh / AI-Native ITSM、ITOM、DevOps、FinOps
    与企业智能运维。
-   已确定的技术路线：Go、Gin、Ent、PostgreSQL、Next.js、TypeScript；此前架构分析还涉及
    Redis、MinIO、Outbox/Worker 等组件，具体以当前代码为准。
-   目标形态：模块化单体优先，不因"平台化"过早拆分微服务。
-   AI-Native 架构理念：Guidance、Harness、Skill
    三层协作，并连接业务应用与领域服务。
-   长期产品方向：ITSM Core + MSP/NOC Extension，逐步扩展 Agent
    Runtime、AgentOps、Agent Security / Governance。
-   已知需求线索：服务商内部 NOC /
    工程师工作场景，服务对象包含电信、联通、移动及直客；邮件来件人不一定是最终客户或合同主体。
-   客户资料可能分散于 PDF 合同、Excel
    客户/IP/设备清单、PNG/JPG/Visio/EDDX 拓扑图、Word 文档及上门工单。
-   邮件自动工单核验的关键字段包括客户/分部名称、合同号、合同状态（执行中/已终止）。
-   曾提出使用闲置 RTX 2080 Ti 进行 PoC
    验证，生产环境使用客户自有算力；该条件需在具体客户项目中重新确认。
-   已知产品改进关注点：工单类型需要租户级自定义；前端卡死和 CPU
    飙升属于优先稳定性问题；工单类型不应仅依赖前端静态 preset。
-   过往架构评估曾指出需关注后端 controller/handler 双架构、handler
    直接访问 Ent、service 过大、BPMN Runtime 边界、AI 能力
    ownership、Command/Event/Outbox 统一、OpenAPI
    生成、前端大组件、OpenTelemetry 和 Connector
    平台等问题。这些属于待复核清单，不应未经代码核对就视为当前缺陷。

### 1.2 现状与规划必须分开

在 README、官网、销售材料和 Roadmap 中，严格区分：

-   **已实现（Implemented）：** 主分支可运行、有测试或可复现证据。
-   **试验中（Experimental）：** 有原型或局部实现，但不承诺生产可用。
-   **规划中（Planned）：** 尚未实现。
-   **商业版能力（Commercial）：** 明确说明授权、交付与支持边界。
-   **客户定制（Custom）：** 不应伪装成通用产品功能。

禁止将架构愿景描述为当前产品能力，禁止使用未经验证的客户案例、性能数字、节省比例或生产可靠性承诺。

## 2. 市场定位与目标客户

### 2.1 核心定位

建议采用一句话定位：

> CloudMesh 是面向企业 IT 服务团队、MSP 与 NOC 的 AI-Native ITSM/IT
> Operations
> 平台，帮助团队把邮件、告警、客户资料、资产、知识和运维操作连接成可追踪、可审批、可审计的服务闭环。

不要将定位写成"全能企业 AI 平台""下一代操作系统"或"通用 Agent
平台"。这类表述范围过大，难以对应明确预算和采购场景。

### 2.2 第一阶段理想客户画像（ICP）

优先验证以下客户，而非把所有企业都当成目标市场：

  ----------------------------------------------------------------------------------------
  维度                                优先客户特征
  ----------------------------------- ----------------------------------------------------
  企业类型                            IT 服务商、MSP、系统集成商、企业内部 IT/NOC 团队

  业务特征                            多客户、多分部、多合同、多设备、多渠道报障

  运维复杂度                          监控、工单、CMDB、知识和邮件分散

  团队规模                            有专职运维/服务台/网络工程师，规模以访谈验证

  现有系统                            老旧 ITSM、Excel、邮箱、IM、监控平台并存

  采购触发点                          老系统替换、工单效率低、审计要求、服务规模扩大、AI
                                      自动化预算

  决策角色                            IT 负责人、NOC 负责人、服务交付负责人、CTO、MSP
                                      业务负责人
  ----------------------------------------------------------------------------------------

### 2.3 首要细分市场

建议先选择 **MSP / IT 服务商 / NOC 服务团队**，原因：

1.  工单、客户、合同、设备、IP、拓扑和服务过程是其日常核心业务。
2.  多客户、多分部和合同有效性校验具有明显的行业场景特征。
3.  邮件转工单、客户识别、工单分派和知识匹配可形成清晰演示。
4.  该场景可进一步连接 Incident、Problem、Change、CMDB 和自动化运维。
5.  相比一开始面向大型集团 CIO
    销售通用平台，更容易找到具体业务负责人进行需求验证。

### 2.4 购买角色与价值主张

  ---------------------------------------------------------------------------------------
  角色                    关注点                         CloudMesh 价值
  ----------------------- ------------------------------ --------------------------------
  NOC/运维经理            响应速度、工单积压、值班效率   自动分类、关联上下文、建议分派

  服务交付负责人          SLA、客户满意度、服务成本      服务过程可视化、SLA 与审计

  IT 负责人               系统整合、稳定性、权限         统一 ITSM/CMDB/事件入口

  一线工程师              减少重复录入、快速定位         自动收集上下文、知识推荐

  安全/审计人员           谁在何时执行了什么             权限策略、审批和审计证据

  MSP 管理层              单客户交付成本、规模化         多客户管理、模板化服务流程
  ---------------------------------------------------------------------------------------

### 2.5 暂不优先进入的市场

-   通用个人 AI 助手。
-   通用低代码 Agent Builder。
-   与云厂商正面竞争基础模型和算力。
-   一开始替换 ERP、MES、CRM 等核心业务系统。
-   需要大量硬件、现场实施或行业认证的重型工业 AI 项目。
-   没有明确预算负责人、只愿意免费试用的泛 AI 创新项目。

## 3. 产品战略与版本体系

### 3.1 产品分层

建议将产品分为三层，但品牌和核心平台保持统一。

#### A. CloudMesh Service Desk（商业入口）

第一阶段核心产品，解决明确的 IT 服务管理问题：

-   Ticket / Request / Incident 基础流程。
-   租户级可配置工单类型。
-   动态表单、分类、优先级、分派规则。
-   SLA、状态流转、通知和审计。
-   客户、分部、合同、联系人关系。
-   CMDB 基础资产与关系。
-   Knowledge Base。
-   Email / Webhook / Alert Connector。
-   AI 邮件解析、客户匹配、工单草稿和知识推荐。

#### B. CloudMesh AgentOps（扩展产品）

在真实客户工作流验证后建设：

-   Agent Runtime / Task Runtime。
-   Skill Registry、版本与权限声明。
-   Action / Tool Registry。
-   ActionFlow / 状态机执行。
-   Memory / Context Engine。
-   Agent Trace、Evaluation、Cost Tracking。
-   任务重试、幂等、超时、取消和补偿。
-   Human-in-the-loop 审批。

#### C. CloudMesh Governance（高价值企业能力）

以客户的真实治理需求为前提逐步推出：

-   Agent Identity。
-   Tenant / User / Service Identity。
-   RBAC / ABAC / Policy Engine。
-   Tool-level Authorization。
-   Secret Reference 与凭据隔离。
-   风险分级与审批策略。
-   不可抵赖审计记录。
-   执行证据、策略版本和回放。
-   多租户隔离、SSO、LDAP/OIDC。
-   企业部署、安全加固和合规支持。

### 3.2 版本边界

  能力                Community   Professional   Enterprise
  ------------------- ----------- -------------- ------------
  基础工单与知识库    ✓           ✓              ✓
  基础 CMDB           ✓           ✓              ✓
  基础 Connector      ✓           ✓              ✓
  AI 邮件转工单       基础/受限   ✓              ✓
  SLA 与自动分派      基础        ✓              ✓
  Agent Trace         基础        ✓              ✓
  高级 Policy         ---         基础           ✓
  SSO / LDAP          ---         可选           ✓
  高级审计与合规      ---         ---            ✓
  多环境/高可用部署   社区自助    标准支持       ✓
  企业 SLA 与支持     社区支持    标准支持       合同约定
  专属集成            社区扩展    付费服务       付费服务

版本边界应以真实维护成本和客户需求决定。不要为了制造商业版差异而人为削弱基础安全能力；身份校验、租户隔离、基本审计和安全默认值应属于产品底线。

### 3.3 首个可收费工作流：AI Email-to-Ticket

建议将其作为第一个产品化闭环：

1.  Email Connector 接收邮件及附件。
2.  保存原始 Message、附件元数据和来源信息。
3.  解析发件人、主题、正文、客户线索、故障描述。
4.  解析 PDF 合同、Excel 客户/设备/IP 清单及必要的 Word 文档。
5.  通过客户、分部、合同号和合同状态进行实体匹配。
6.  判断发件方、最终客户、合同主体和服务对象之间的关系，不得默认发件人就是客户。
7.  关联资产、知识库、历史工单和服务记录。
8.  生成工单草稿、分类、优先级和分派建议。
9.  对低置信度、客户身份冲突、合同状态不明确等情况转人工确认。
10. 人工确认后创建工单并发送回执。
11. 记录模型版本、提示版本、检索证据、字段置信度、人工修改和最终结果。

**产品验收重点：**
不只是"模型能解析邮件"，而是客户匹配准确、工单字段可校验、异常能转人工、重复邮件不重复建单、全过程可追踪。

### 3.4 产品路线图

  -------------------------------------------------------------------------------------------------------
  阶段                    重点                                             进入下一阶段的条件
  ----------------------- ------------------------------------------------ ------------------------------
  R0：稳定化              前端性能、后端分层、工单类型配置、租户边界       核心流程稳定，回归测试可重复

  R1：Service Desk        邮件、客户、合同、工单、知识、CMDB               至少一个客户完成端到端 PoC

  R2：NOC Operations      Alert→Event→Incident、Timeline、SLA、值班/分派   客户愿意持续使用并付费

  R3：AgentOps            Skill、Runtime、ActionFlow、Trace、Evaluation    有多个真实 Agent 工作流

  R4：Governance          Identity、Policy、Approval、Audit、Secret        客户提出明确治理采购需求

  R5：扩展                FinOps、数据库运维、变更风险、更多 Connector     现有客户增购或渠道验证
  -------------------------------------------------------------------------------------------------------

不要仅按日历时间推进。每一阶段都必须有客户验证和质量门槛。

## 4. 产品架构与工程治理原则

### 4.1 架构原则

1.  模块化单体优先，先清晰边界再考虑服务拆分。
2.  业务领域模型与 Agent 技术框架解耦。
3.  AI 输出必须经过 schema 校验和业务规则校验。
4.  Agent 不得绕过 Application Service 直接访问数据库或生产工具。
5.  所有有副作用的操作必须进入统一执行入口。
6.  Connector、Skill、Action 都要有版本、权限、超时和错误语义。
7.  关键业务事件采用可靠投递机制；需要时使用 Outbox/Worker。
8.  先使用 PostgreSQL/pgvector 等现有基础设施，避免早期引入过多组件。
9.  通过 OpenTelemetry、结构化日志和指标形成可观测性。
10. 安全、租户隔离、审计和备份恢复是产品能力，不是最后补丁。

### 4.2 Guidance--Harness--Skill 三层架构

#### Guidance：约束目标与决策边界

负责：

-   Agent 目标、任务上下文和业务规则。
-   允许/禁止事项。
-   输出 Schema。
-   风险等级和审批要求。
-   置信度阈值与升级人工条件。

Guidance 不应承载可执行代码，也不应替代后端权限校验。

#### Harness：控制执行生命周期

负责：

-   Runtime 生命周期。
-   上下文装配。
-   模型路由和预算。
-   Tool 调用调度。
-   超时、重试、取消、幂等。
-   Policy 检查和审批。
-   结果验证、Trace 和审计。

Harness 是可靠执行边界，不能把权限控制只放在 Prompt 中。

#### Skill：可复用的任务能力

每个 Skill 应包含：

-   名称、用途、版本和维护者。
-   输入/输出 Schema。
-   前置条件和权限声明。
-   使用的 Tool/Connector。
-   风险级别。
-   超时、重试和幂等策略。
-   测试用例和评测数据。
-   文档、变更记录和兼容性说明。

Skill 不是任意 Shell 脚本集合。执行能力应通过受控 Tool/API 暴露。

### 4.3 关键领域边界

建议逐步明确以下模块：

-   Identity & Tenant。
-   Ticket / Request。
-   Incident / Problem / Change。
-   Customer / Contract / Contact。
-   CMDB / Asset / Relationship。
-   Knowledge。
-   SLA / Assignment / Schedule。
-   Connector / Inbound Message。
-   Agent / Skill / Runtime。
-   Action / Approval / Execution。
-   Policy / Audit。
-   Notification。
-   Reporting / Analytics。

避免出现 controller、handler、service、workflow、AI
模块各自重复实现业务规则的情况。所有写操作应有统一的 Application Service
/ Command 边界。

### 4.4 生产执行安全基线

-   默认只读；写操作按风险等级授权。
-   Agent 身份与最终用户身份分离并可追踪。
-   每次执行记录 tenant、actor、agent、skill、tool、policy
    version、input/output 摘要和结果。
-   Secret 不进入 Prompt、日志、Trace 或普通业务表。
-   高风险操作要求审批或显式策略授权。
-   对生产操作提供 dry-run、执行前校验、幂等键和结果验证。
-   对支持的操作设计回滚或补偿；不能回滚时明确告知风险。
-   限制最大步骤数、Token、时间、并发和费用。
-   防止 Prompt Injection 通过邮件、附件、网页和知识库内容扩大工具权限。
-   将不可信内容视为数据，而不是系统指令。

## 5. 商业模式与定价策略

### 5.1 收入结构

采用四类收入组合：

1.  **软件订阅/许可：** Professional、Enterprise 年度授权。
2.  **私有化部署：** 安装、环境适配、升级和高可用部署。
3.  **专业服务：** Connector、数据迁移、流程配置、Skill 开发和培训。
4.  **持续支持：** 年度运维、SLA、版本升级和托管服务。

长期目标是提高软件许可和持续支持收入占比，降低一次性定制开发依赖。

### 5.2 初期建议价格（待客户验证）

以下仅作为报价实验起点，需根据客户规模、部署模式、支持范围和采购预算调整。

  产品/服务                           建议测试价格
  --------------------- --------------------------
  Community                                   免费
  Professional                  1.98--4.98 万元/年
  Enterprise                       8--20 万元/年起
  私有化部署与初始化                 10--30 万元起
  付费 PoC                        1.5--3 万元/项目
  专项 Connector/集成              2--10 万元/项目
  年度支持                按许可金额或服务范围报价

避免将以上数字宣传为市场标准价。报价前先确定用户数、并发、工单量、租户数、环境数、模型费用、支持时段、升级范围和数据责任。

### 5.3 PoC 商业规则

每个 PoC 必须有：

-   明确的业务负责人和技术负责人。
-   真实但脱敏或授权的数据样本。
-   明确的范围和排除项。
-   2--4 周建议周期。
-   基线数据和验收指标。
-   客户提供的系统、账号、网络和数据条件。
-   费用、付款节点和变更控制。
-   PoC 结束后的正式采购决策时间。

PoC 验收示例：

  指标             定义
  ---------------- -------------------------------------------
  邮件解析成功率   成功解析必要字段的邮件数 / 有效测试邮件数
  客户匹配准确率   正确匹配客户/分部/合同的样本数 / 样本总数
  工单字段准确率   通过业务校验的关键字段数 / 关键字段总数
  重复建单率       重复邮件导致重复工单数 / 应去重邮件数
  人工节省时间     PoC 前后相同任务的人工处理时间差
  审计完整率       可关联完整执行证据的操作数 / 总操作数

不要只用模型回答准确率作为验收标准。

### 5.4 单客户经济模型

每个合同至少核算：

-   软件收入。
-   实施收入。
-   年度支持收入。
-   云资源和模型 API 成本。
-   实施工时。
-   售后工时。
-   第三方服务成本。
-   渠道佣金。
-   回款周期和坏账风险。

建议跟踪：

-   ARR / MRR。
-   软件收入占比。
-   项目毛利率。
-   交付工时/客户。
-   客户获取成本（CAC）。
-   回款周期。
-   续费率和扩容收入。
-   PoC 转正式合同率。

不要把一次性实施收入重复计入
ARR。创始人的研发和交付劳动也应在内部经济模型中计价，即使初期没有实际发薪。

## 6. 开源运营战略

### 6.1 开源的商业目的

开源不是简单地免费发布代码。它应服务于：

1.  建立技术可信度。
2.  降低客户评估和试用门槛。
3.  获取开发者和潜在客户反馈。
4.  形成 Connector、Skill 和文档生态。
5.  为商业版提供自然线索。
6.  形成长期品牌资产。

### 6.2 开源与商业版边界

建议遵循"开放核心能力、商业化企业复杂度"的原则，但必须保持开源版本身安全、可用、有价值。

开源版应具备：

-   核心 ITSM 业务能力。
-   基本 CMDB 和知识库。
-   基础 Connector 扩展机制。
-   基本租户隔离和权限。
-   可本地部署。
-   可导出数据。
-   基本审计能力。
-   可运行的 Demo 和测试。

商业版可提供：

-   高级 SSO / LDAP / OIDC 集成。
-   高级策略管理和合规报表。
-   企业多环境管理。
-   高可用与灾备方案。
-   高级审计、保留策略和报表。
-   企业级升级、支持和 SLA。
-   专属 Connector 与实施服务。

安全底线、数据可迁移性和基本审计不应被人为锁在付费版中。商业版差异应建立在企业级管理、规模、支持和合规复杂度上。

### 6.3 许可证与知识产权治理

在明确商业模式前，应核查当前仓库 LICENSE、依赖许可证、商标和贡献协议。

需要决策：

-   采用宽松许可证还是带商业限制的开源许可证。
-   是否需要 Contributor License Agreement（CLA）或 Developer
    Certificate of Origin（DCO）。
-   商业版是否采用独立仓库、私有模块或商业插件。
-   商标、产品名称、Logo 和文档版权归属。
-   第三方依赖的许可证兼容性。

不得在未核查现有许可证的情况下承诺商业再授权、闭源分发或 OEM 权利。

### 6.4 GitHub 仓库运营标准

仓库首页应包含：

1.  一句话产品定位。
2.  适用客户和使用场景。
3.  真实产品截图或短视频。
4.  3 分钟快速体验。
5.  Docker Compose 安装。
6.  架构图和核心模块说明。
7.  功能状态矩阵（已实现/实验/规划）。
8.  Roadmap。
9.  Issue / PR 模板。
10. 安全漏洞披露方式。
11. 贡献指南。
12. 商业服务与联系入口。

建议建立：

-   `README.md`
-   `CONTRIBUTING.md`
-   `CODE_OF_CONDUCT.md`
-   `SECURITY.md`
-   `CHANGELOG.md`
-   `ROADMAP.md`
-   `docs/architecture/`
-   `docs/deployment/`
-   `docs/user-guide/`
-   `.github/ISSUE_TEMPLATE/`
-   `.github/PULL_REQUEST_TEMPLATE.md`

### 6.5 Issue 与社区响应机制

建议 Issue 标签：

-   `type:bug`
-   `type:feature`
-   `type:question`
-   `type:docs`
-   `area:backend`
-   `area:frontend`
-   `area:agent`
-   `area:itsm`
-   `area:cmdb`
-   `area:connector`
-   `priority:p0` 至 `priority:p3`
-   `status:triage`
-   `status:planned`
-   `status:in-progress`
-   `status:blocked`
-   `good first issue`

响应原则：

-   安全问题走私密披露流程，不在公开 Issue 暴露利用细节。
-   Bug 必须尽可能要求版本、复现步骤、日志和环境信息。
-   Feature Request 必须描述用户问题，而不仅是指定技术实现。
-   不承诺未排期功能的交付日期。
-   每周至少进行一次 Issue triage。
-   每个版本发布说明应明确新增、修复、破坏性变化和升级步骤。

### 6.6 开源运营指标

不要只追求 GitHub Stars。建议分层衡量：

  层次       指标
  ---------- ----------------------------------------
  曝光       仓库访问、README 转化、文档访问
  试用       Clone、镜像拉取、Demo 启动、安装成功率
  活跃       活跃部署、Issue、Discussion、PR
  产品价值   完成核心工作流的用户数、反馈质量
  商业转化   企业线索、需求访谈、PoC、付费合同
  社区健康   首次响应时间、PR 合并周期、贡献者留存

Stars 只是曝光指标，不能替代活跃部署和付费客户。

## 7. 内容营销与品牌运营

### 7.1 内容定位

建议围绕"企业 AI
工作流与行业智能化"建立专业内容体系，技术内容服务于产品认知和商业线索，而不是单纯追逐热点。

### 7.2 四个内容支柱

  内容支柱               示例主题                            对应产品能力
  ---------------------- ----------------------------------- --------------
  AI-Native ITSM         传统 ITSM 如何演进为 Agent 驱动     Service Desk

  Agent Security         Tool 权限、Prompt Injection、审计   Governance
  AI for IT Operations   告警关联、RCA、变更风险、FinOps     ITOM

### 7.3 内容转化路径

每篇文章尽量形成：

**行业问题 → 技术原理 → 架构方案 → 可运行 Demo → 开源仓库 →
需求征集/企业咨询。**

文章结尾不应只放 GitHub 链接，而应明确读者下一步能做什么：

-   部署 Demo。
-   提交场景需求。
-   参与 Roadmap 讨论。
-   申请企业 PoC。
-   联系商业支持。

内容中必须区分真实产品能力、实验原型和概念设计，不得编造客户案例。

### 7.4 建议发布节奏

以可持续为原则：

-   每周 1 篇深度技术文章。
-   每周 1 次项目开发日志或版本更新。
-   每两周 1 个可复现 Demo。
-   每月 1 份 Roadmap / 社区进展。
-   每季度 1 份产品与行业研究报告。

质量和可复现性优先于发布数量。

## 8. 销售与渠道策略

### 8.1 第一批客户从哪里来

优先顺序：

1.  已有需求交流和项目线索。
2.  IT 服务商、MSP、NOC 服务商。
3.  云原生和数据库服务商。
4.  GitHub 使用者和公众号读者中的企业负责人。
5.  系统集成商和企业软件实施商。
6.  通过公开内容主动开发的目标客户。

### 8.2 首批客户开发流程

1.  建立 30--50 家目标客户清单。
2.  识别 IT/NOC/服务交付负责人。
3.  先访谈业务流程，不先推销平台。
4.  记录工单量、渠道、客户资料、合同核验、SLA 和人工处理时间。
5.  选择一个可量化场景。
6.  演示真实工作流。
7.  签订有边界的付费 PoC。
8.  形成验收报告。
9.  转年度许可、私有化或支持合同。
10. 将通用需求回流产品 Roadmap。

### 8.3 渠道合作

可与以下伙伴合作：

-   IT 运维外包商。
-   MSP / 云管理服务商。
-   Kubernetes / 云原生服务商。
-   数据库服务商。
-   ITSM 实施商。
-   安全服务商。

合作形式：

-   联合 PoC。
-   渠道转售。
-   OEM / 白标（需许可证和商标规则允许）。
-   Connector 联合开发。
-   年度支持分成。

渠道佣金和责任必须写入合同，明确售前、交付、售后、客户数据和续费归属。

### 8.4 销售材料清单

至少准备：

-   1 页产品介绍。
-   10 页以内产品演示 Deck。
-   3--5 分钟 Demo 视频。
-   产品功能矩阵。
-   部署架构图。
-   安全与数据处理说明。
-   PoC 方案与验收模板。
-   报价单。
-   合同/SOW 模板。
-   客户需求访谈表。

## 9. 90 天执行计划

### 第 1--15 天：定位与客户验证

**目标：确定一个真实付费场景。**

任务：

-   复核当前仓库主分支、功能、CI、Issue 和架构。
-   访谈 10--15 位目标用户/负责人。
-   梳理现有 ITSM、NOC 和邮件工单流程。
-   确定 ICP、购买角色和预算来源。
-   完成 AI Email-to-Ticket PRD。
-   建立竞争产品对比表。
-   明确 PoC 报价、范围和验收指标。

验收：

-   至少 3 个客户愿意进入产品演示或 PoC 讨论。
-   关键流程和数据来源已明确。
-   产品范围冻结。

### 第 16--30 天：完成可演示 MVP

**目标：一封邮件形成可人工确认的工单。**

范围：

-   Email Connector。
-   Message / Conversation 记录。
-   附件元数据与解析。
-   客户/分部/合同匹配。
-   知识检索。
-   工单草稿。
-   人工确认。
-   创建工单与邮件回执。
-   幂等、错误处理和审计。

验收：

-   使用一组脱敏测试邮件完成端到端演示。
-   能识别客户不确定、合同无效、信息缺失等异常。
-   不会因重复投递而重复创建工单。

### 第 31--45 天：真实客户 PoC

**目标：验证客户数据和真实工作流。**

任务：

-   确认数据授权和脱敏。
-   部署测试环境。
-   导入少量合同、客户、设备和历史工单。
-   建立基准测试集。
-   记录字段准确率、客户匹配率、人工节省时间和失败类型。
-   组织用户验收。

验收：

-   客户认可业务价值。
-   形成量化 PoC 报告。
-   记录必须修复项与商业采购条件。

### 第 46--60 天：商业化包装

**目标：将 PoC 整理成可重复销售产品。**

任务：

-   完善安装和升级流程。
-   补齐租户隔离、RBAC、审计和备份。
-   完成产品功能矩阵。
-   建立版本和授权机制。
-   完成报价、SOW、PoC 合同模板。
-   整理客户部署手册和故障排查文档。

验收：

-   新客户部署不依赖开发者手工改代码。
-   产品边界、价格和支持范围清晰。
-   至少一个付费验证机会进入采购流程。

### 第 61--90 天：开源运营与销售复制

**目标：形成产品分发和商业转化闭环。**

任务：

-   优化 GitHub README、Roadmap、Issue 模板。
-   发布稳定版本和变更日志。
-   发布 3 篇产品相关深度文章。
-   发布演示视频和部署教程。
-   建立 30--50 家目标客户名单。
-   拓展 2--3 家渠道伙伴。
-   推进第二、第三家客户演示。
-   复盘 PoC 转化和交付工时。

### 90 天成功标准

-   一个可部署、可演示、可复现的 MVP。
-   10--15 次有效客户访谈。
-   至少 3 家设计/验证客户。
-   至少 1 家真实客户完成 PoC。
-   争取获得第一笔付费 PoC 或软件收入。
-   一套可复用的产品文档、销售材料和开源运营机制。

如果未获得付费，不应直接扩大研发投入，而应回到客户问题、预算、采购路径和
ROI 重新验证。

## 11. 产品决策机制：如何判断一个功能是否值得开发

每个需求必须回答以下问题：

1.  哪类用户提出？
2.  对应哪个真实工作流？
3.  当前如何解决？
4.  问题发生频率和成本是什么？
5.  是否有预算负责人？
6.  是否可被多个客户复用？
7.  是否属于核心领域能力？
8.  是否增加安全、维护或部署复杂度？
9.  是否已有开源组件或现有功能可满足？
10. 如何定义验收标准？

建议评分：

  维度               权重
  ---------------- ------
  客户痛点强度        25%
  付费可能性          20%
  多客户复用性        20%
  战略一致性          15%
  研发成本与风险      10%
  维护成本            10%

评分只是辅助决策。安全漏洞、数据丢失、租户隔离和核心稳定性问题属于强制优先事项，不应因商业评分低而延后。

### 明确不做清单

-   不为追热点而接入每一个模型或 Agent 框架。
-   不在没有客户验证时建设通用 Agent Marketplace。
-   不在 MVP 阶段拆成大量微服务。
-   不将 Prompt 当作权限控制。
-   不让 Agent 直接持有长期高权限凭据。
-   不承诺未经验证的准确率、节省比例或 SLA。
-   不接受无限范围的免费 PoC。
-   不把客户专属代码直接合并进核心产品而不做抽象。
-   不以 GitHub Stars 作为唯一成功指标。

接下来不要同时启动所有规划模块。建议按以下顺序执行：

**第一步：复核现有仓库。** 对照本文件建立"已实现 / 不完整 / 缺失 /
有缺陷"矩阵，尤其检查稳定性、工单类型动态配置、租户边界、后端分层和现有
AI 能力。

**第二步：锁定一个首发场景。** 优先验证 AI Email-to-Ticket，特别是
MSP/NOC 的客户、分部、合同和服务对象识别。

**第三步：定义付费 PoC。**
以真实业务数据、可量化指标、明确周期和费用作为商业验证，不以免费演示代替销售。

**第四步：把通用能力沉淀回产品。** 将客户需求抽象为
Connector、Skill、配置、领域模型和执行策略，避免形成客户专属分支。

**第五步：建立开源运营闭环。**
每个版本都应有可运行成果、文档、演示、变更记录和社区反馈入口。

**第六步：用数据决定扩张。** 只有当 Service Desk
有稳定客户和复用需求后，再增加
AgentOps；只有当客户出现明确治理预算后，再扩展 Governance。

### 战略北极星

> **让 CloudMesh 成为企业 IT 服务与运维团队可信赖的 AI
> 执行平台：从工单和事件进入业务，从 Agent 和 Skill
> 提升效率，以权限、审计和可靠执行建立企业信任。**

商业成功的判断标准不是功能数量、代码行数或模型调用量，而是客户是否持续使用、是否愿意续费、交付是否可以复制，以及开源社区是否能够持续带来真实用户和商业机会。
