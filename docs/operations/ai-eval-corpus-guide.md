# AI 质量验收：真实知识库语料准备指南

> 适用版本：v1.7 起。代码事实源：`itsm-backend/ai/eval/corpus.go`、
> `itsm-backend/ai/eval/datasets/`、`itsm-backend/cmd/ai-eval/`、
> `itsm-backend/service/rag_service.go`（keywordSearch）。

本文回答一件事：**为 AI 能力的 LLM 档验收（`cmd/ai-eval -mode llm`）准备
真实知识库语料时，语料要满足什么格式与质量要求，怎么准备、怎么标注、
怎么跑验收。**

AI 能力当前维持 Pilot 的唯一代码侧剩余阻断是：真实 LLM 与真实知识库语料
的质量验收尚未由人执行并归档。仓库自带的 `datasets/corpus/rag_corpus.jsonl`
（21 篇）形状真实但内容是合成的——它验证的是「评测框架与检索链路」，
不是「真实知识库的召回质量」。这份指南就是补齐后者的操作手册。

---

## 1. 语料的角色：库里有什么 vs 该检索到什么

评测把两件事严格分离，**不要混在一个文件里**：

| 文件 | 回答的问题 | 谁产出的 |
|:---|:---|:---|
| `rag_corpus.jsonl`（语料） | 知识库里**有什么文章** | 生产库导出或人工编写 |
| `rag.jsonl`（用例） | 每个问题**该检索到哪几篇** | 知识库维护者**人工标注** |

两者混写会导致「为了命中而写语料」的自我循环——语料必须独立于断言存在。
用例的 `expected_refs` 引用**文章标题**（不是库主键），这让同一份数据集既能
在 CI 内存库跑，也能在真实生产库验收时复用。

## 2. 硬性格式约束（装载代码强制）

语料是 JSONL，每行一篇知识文章，字段与生产 `KnowledgeArticle` 表同形：

```json
{"title":"VPN 证书过期处理流程","content":"本文回答 VPN 证书过期怎么办：……","category":"网络与基础设施","tags":"VPN,证书,故障处理"}
```

| 字段 | 类型 | 约束 |
|:---|:---|:---|
| `title` | string | **非空**（空标题装载直接报错）。期望引用按标题归一化匹配，须与用例 `expected_refs` 对得上 |
| `content` | string | 正文。见 §3：query 原话必须完整出现在标题或正文里，否则检索不可能命中 |
| `category` | string | 真实分类。检索带分类可见性过滤，空分类走最保守分支 |
| `tags` | string | **逗号分隔字符串**（`"VPN,证书"`），不是数组——与生产字段同形 |
| `published` | bool | 默认 `true`。**未发布的文章不进 RAG 结果**（生产语义，草稿必须排除） |
| `tenant_id` | int | 默认 1；生产验收时对准真实租户 ID |

配套用例（`rag.jsonl`）每行：

```json
{"id":"rag-101","query":"VPN 证书过期怎么办","tenant_id":1,"top_k":3,"expected_refs":["VPN 证书过期处理流程"],"min_relevance":0.7,"corpus_tenant_id":1}
```

守卫会检查（不满足 CI 直接红）：

- 每个用例的 `expected_refs` 必须指向语料里**真实存在的标题**；
- 语料量必须**大于**期望文章去重数——只有期望文章、没有干扰文章的语料
  没有区分力（任何检索器都满分）；
- 检索器查询计数 ≥ 用例数（候选必须真来自检索，机制性判据）。

## 3. 最关键的一条：检索语义决定内容怎么写

生产的关键词检索是**整串包含**匹配（SQL 的
`TitleContainsFold(query) OR ContentContainsFold(query)`），不是分词搜索。
这直接决定了期望文章的写法：

- **期望命中的文章**：标题或正文必须包含用户问题的**原话**。比如 query
  是「VPN 证书过期怎么办」，期望文章正文里应自然出现这句原话（真实的 FAQ
  文章天然如此，因为本来就是写给问这个问题的人看的）。
- **干扰文章**（必须有，两类都要）：
  1. *语义相近但不含 query 原文*——真实语料的大多数。检验检索不误召回；
  2. *同含 query 原文但不是标准答案*——比如 query「如何配置 CDN 缓存」同时
     命中《CDN 缓存配置指南》（期望）与《CDN 缓存容量规划与预热策略》（同
     含原话但不是本问题的标准答案）。这是让 top_k 有真实区分度的关键，
     也是真实知识库的常态：一个问题命中多篇。

## 4. 内容质量要求（让验收有真实意义）

| 维度 | 要求 |
|:---|:---|
| 来源 | 生产知识库的真实沉淀：故障处理手册、配置指南、流程说明、FAQ。不要用生成的文本充数 |
| 体量 | 建议 **30–100 篇已发布文章 + 20–50 个典型问题**（少于 20 个用例统计波动大，一次未命中就掉 5 个百分点） |
| 问题多样性 | 三种问法都要有：操作式（「如何配置 X」）、故障式（「X 报错怎么办」）、概念式（「X 和 Y 的区别」）。query 应来自**真实服务台工单里用户实际问的问题**，不是拍脑袋编的 |
| 标注依据 | 每个用例能回答「为什么期望是这几篇」。由知识库维护者标注（预测数据集有 `annotation_basis` 字段先例），标注人可追溯 |
| 难度分布 | 必须含**难例**：多篇相似文章竞争、术语与口语混用（用户问「服务器连不上」而文章写「EC2 实例网络不通」）。全是用词一致的简单例会让召回率虚高，验收没有信息量 |
| 期望占比 | 期望文章占少数（多数文章是干扰），否则任何检索器都能拿高分 |

## 5. 准备路径

### 路径 A（推荐）：从生产库导出

```bash
# 1. 导出指定租户的已发布文章为语料格式（见 §6 命令说明）
go run ./cmd/ai-eval -export-corpus -tenant 1 -out-datasets ./my-eval

# 2. 从服务台工单挑 20-50 个真实高频问题，写成 rag.jsonl 的 query

# 3. 知识库维护者对每个问题标注 expected_refs（哪几篇是正确参考）
#    标注时回答：一个合格的工程师被问到这个问题，应该读哪几篇？

# 4. 把两份文件放进 datasets/（或用 -datasets 指定目录），跑 LLM 档验收
go run ./cmd/ai-eval -mode llm -datasets ./my-eval -out ./ai-eval-report-prod
```

### 路径 B：人工编写 FAQ 集

找运维/服务台同事按 §2/§3 写典型问题与标准文章，顺带作为新租户的知识库
种子。缺点是天然缺真实干扰项——建议混入路径 A 的存量文章一起用。

## 6. 导出命令说明

`-export-corpus` 只导出**语料**（库里有什么），不产出期望引用——「该检索
到什么」必须由人标注，这一步没有捷径，也不应该有（自动生成的期望会把
「检索器的现状」当成「正确答案」，验收就失去意义了）。

导出条件与检索的可见性语义一致：仅已发布、未软删、指定租户的文章。

## 7. 验收执行与归档

```bash
# LLM 档（读 llm.* 配置构造真实 provider；配置缺失报错，不悄悄降级）
go run ./cmd/ai-eval -mode llm -datasets <目录> -out <报告目录>
```

- 输出 JSON 报告：每项评测的指标、样本数、模式、候选来源，附机器可读
  结论（`passed / mode / basis`）；
- **退出码 0 只代表报告产出，不代表指标达标**——是否达标由验收人对照
  阈值判断（RAG 召回率建议 ≥0.8，参考 CI 门禁口径）；
- 报告归档（目录含时间戳），归档动作即「人工验收已执行」的证据，也是
  AI 能力 pilotReason 里「尚未由人执行过」这条阻断的解除条件。

## 8. 常见错误

| 错误 | 后果 |
|:---|:---|
| 期望引用的标题与语料标题对不上（多一个空格、全角半角差异） | 归一化能兜住大小写与空白，但兜不住措辞差异——该用例永远未命中 |
| 语料全是期望文章、没有干扰 | 守卫直接红；即便绕过，召回率恒满分，验收无信息量 |
| query 原话不在任何期望文章的标题/正文里 | 关键词检索不可能命中，该用例召回率贡献为 0 |
| 用生成的文本充当真实语料 | 指标再高也只证明「检索器能检索合成文本」，验收结论不可用 |
| 自动生成 expected_refs（比如按检索结果回填） | 把现状当答案，验收失去意义——期望必须独立于检索器产生 |
