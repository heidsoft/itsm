## 一、产品业务本质与能力基线

### 1.1 我们卖的是什么

不是"工单系统",而是**企业 IT 与设施服务的运营中枢**:把"报障 → 分派 → 处置 → 复盘"与"请求 → 审批 → 交付"两条主链路,加上资产/配置视角(CMDB)、时效视角(SLA)、流程视角(BPMN)组织成一个可审计的闭环。

五个行业的共同购买动机:**服务中断有业务损失,而损失大小决定付费意愿**。行业差异体现在:中断的对象(系统/设备/网点)、响应的组织(倒班/层级/外包)、合规的压力(等保/数据驻留)。

## 二、五行业需求深潜

每个行业按"客户画像 → 典型场景 → 关键诉求 → 现有能力承接 → 差距"展开。

### 2.1 工业制造

**客户画像**:中大型制造企业,信息中心 5-30 人,工厂/车间/产线三级组织,三班倒连续生产。买家是 CIO/信息中心主任;真实用户是车间班组长、工艺工程师、IT 运维。

**典型场景**:
- 产线 MES/SCADA 故障:**停机每分钟都是钱**,必须分钟级响应、越级升级直达值班经理
- ERP/PLM/WMS 等经营系统的日常报障与权限请求
- 设备巡检与保养协同(注意边界:深度设备管理是 EAM 的活,ITSM 做"报修入口 + 工单流转",别越界造 EAM)
- 系统变更避开生产高峰:变更窗口与产线排产联动

**关键诉求**:
1. **停机=最高优先级**的事件分级与升级链(升级矩阵 ✅ 直接命中)
2. **告警自动开单**:产线监控/物联网平台 → 事件,人不报机器报(🔶 待产品化)
3. **倒班场景**:值班交接、夜间无人时段的自动升级(✅ on-call 基础已有)
4. 现场工程师移动端接单(❌ 缺失,车间没有电脑)
5. 与 OT 侧的边界:支持"生产设备"类 CI 即可,不做设备台账主体

**现有承接**:升级矩阵 + on-call + Webhook 雏形 + CMDB CI 类型扩展(产线/设备/工控系统)。
**差距排序**:移动端 > 告警接入产品化 > OT 类 CI 模板。

### 2.2 医疗

**客户画像**:三级医院、医疗集团与区域医联体，信息中心连接临床科室、医学工程、后勤和外部厂商。系统 7x24 运行，服务中断可能影响诊疗连续性，安全边界高于普通办公 IT。

**典型场景**:
- HIS/EMR、PACS、LIS、集成平台故障的重大事件响应与跨厂商协同
- 门诊、急诊、手术、药房等关键区域终端和网络报障
- 医疗设备联网接口故障的服务协同（ITSM 管服务流程与依赖，不替代医疗设备管理系统，更不作临床判断）
- 上线变更、停机维护和应急切换的审批、通知、验证与复盘

**关键诉求**:
1. **诊疗连续性优先**:按业务服务和临床区域评估影响，关键系统采用 7x24 SLA、值班和明确升级链
2. **最小权限与全程审计**:患者健康信息不得进入普通工单、日志、prompt 或 command payload；敏感访问需数据分级、授权、脱敏和审计
3. **受控应急访问**:紧急情况下的 break-glass 必须限时、说明理由、二次审计并自动收回，不能用超级管理员常驻替代
4. **厂商协同隔离**:外部厂商只能访问被委派的医院、系统和工单范围，附件与知识同样执行权限过滤
5. **高风险变更控制**:维护窗、回退预案、业务确认和 PIR 必须成为流程不变量

**现有承接**:事件/变更/PIR、CMDB 影响分析、on-call、知识权限、多租户/MSP 与审计基础。
**差距排序**:敏感数据分级与脱敏验证 > 医疗重大事件模板 > 厂商委派范围 > HIS/EMR/PACS/LIS 连接器。
**准入边界**:完成跨租户/越权回归、备份恢复演练、审计完整性和敏感数据防泄漏验证前，不把产品宣传为医疗生产就绪；AI 只做决策支持，不输出临床结论。

### 2.3 零售

**客户画像**:连锁品牌(便利店/服饰/餐饮),总部信息中心 + 大区 + 数百至数千门店。门店店员是最大用户群但 IT 能力最弱。

**典型场景**:
- **POS/扫码枪/收银系统故障 = 无法收款**,是零售的"停机时刻",要求小时级闭环
- 门店网络、大屏、监控设备的报修与换件
- 总部系统(会员/营销/ERP)支持
- 新店开业的 IT 配套请求(服务目录履约场景)

**关键诉求**:
1. **极简报障入口**:店员不会用复杂系统——飞书/企微消息报障、拍照上传是刚需(🔶 连接器规划中,移动端缺失)
2. **网点层级**:总部→大区→门店,按区域自动分派(✅ `customer_branch` + 分派规则命中)
3. **快换流程**:低值设备不修只换,流程要短(🔶 服务目录模板可承载,需行业模板)
4. **营业时间 SLA**:营业中/打烊后不同时效(✅ SLA 策略可配)
5. 设备资产量大值低:重在位置与状态,不做重资产折旧(与固定资产系统分工)

**现有承接**:网点模型、分派规则、服务目录、飞书连接器——零售与产品既有结构契合度最高。
**差距排序**:移动/IM 报障入口 > 行业模板包 > 设备快换流程。

### 2.4 电商

**客户画像**:中大型电商/品牌电商技术部,云原生团队,工程师文化,倾向自建与开源。决策快、要求高、是开源社区最可能的贡献者群体。

**典型场景**:
- **大促保障(双 11/618)**:变更冻结窗、作战值守、重大事件作战室
- 支付/订单/库存链路故障:分钟级响应、跨团队协同、事后 PIR
- 频繁的发布变更管理:变更日历、风险评估、灰度回滚预案挂接
- 容量/资源类服务请求(与云资源联动)

**关键诉求**:
1. **告警即事件**:监控系统是主要入口,人肉开单不可接受(🔶 最急)
2. **重大事件协同**:作战室、时间线、通报(❌ 缺失,差异化机会)
3. **变更冻结日历**与发布窗口(🔶 变更域有发布窗口概念,日历视图待做)
4. 与 CMDB/云资源的联动影响分析(✅ 云发现 + 影响分析命中)
5. 工程师体验:API 优先、可集成进内部工具链(✅ API 面完整)

**现有承接**:事件生命周期、重大事件升级、CAB、云发现、PIR——ITIL 深度功能与电商诉求最对口。
**差距排序**:告警接入 > 作战室 > 变更冻结日历。
**战略意义**:电商标杆 + 开源贡献者双重价值,建议作为开源社区的旗舰场景。

### 2.5 物流

**客户画像**:快递/快运/供应链企业,总部—省区—分拨中心—网点四级,网点可达万级。IT 团队小但设备多。

**典型场景**:
- 分拣设备故障:直接影响中转时效,夜间分拣高峰是关键时刻
- 巴枪(手持终端)、车载终端、网点网络的报修与调度
- TMS/WMS 等核心系统支持
- 网点搬迁/新开的 IT 配套履约

**关键诉求**:
1. **网点海量且层级深**:四级组织、按路由/区域分派(✅ 网点模型 + 分派规则,但需验证万级网点下的列表与搜索性能)
2. **时效升级**:快件时效文化渗透到 IT 服务——超区/超时自动升级(✅ 升级矩阵命中)
3. **移动优先**:网点与司机没有电脑,全靠手机(❌ 缺失,比零售更刚)
4. 终端设备库存与换件调度(🔶 资产+履约流程组合)
5. 7x24 值班与夜间应急(✅ on-call)

**现有承接**:网点模型、升级矩阵、on-call、服务目录履约。
**差距排序**:移动端 > 万级网点性能验证 > 设备换件调度模板。

## 五、产品策略建议

### 5.1 行业包架构(不 fork 原则的落地)

每个行业包 = **纯配置资产**,由四类种子组成,全部走现有扩展点:

1. 工单类型集(类型 + 自定义字段 + 分派规则)
2. 服务目录模板(行业服务项 + 审批路由)
3. BPMN 流程模板 + SLA 策略模板(营业时段/7x24/停机时效)
4. CMDB CI 类型包(工业:产线/工控;医疗:业务服务/院区/临床系统/接口;零售:POS/门店设备;物流:分拣机/巴枪/网点;电商:云资源/应用服务)

交付要求:幂等导入、可版本升级、只造模板不造假数据(与现有种子规范一致)。

### 5.2 切入次序(修订后)

| 次序 | 行业 | 理由 | 打法 |
|---|---|---|---|
| 1 | **零售 + 电商**(一组) | 与网点模型/事件深度最契合;电商带开源声量,零售带 MSP 渠道 | 零售模板包先行(已决策),电商做开源旗舰案例 |
| 2 | **物流** | 与零售共用 80% 能力(网点+移动+换件),边际成本低 | 复用零售包 + 万级网点性能专项 |
| 3 | **工业** | 需告警接入与作战室支撑,排在共性差距 #2/#3 完成后 | 标杆工厂试点,绑定设备报修场景 |
| 4 | **医疗** | 对连续性、隐私和审计要求最高，应在平台可靠性与安全门禁成熟后进入 | 与医院信息中心和医学工程共创，只从非临床决策的 IT 服务场景试点 |

### 5.3 与 MSP 模式的商业闭环

零售/物流的现实是:**大量门店/网点的 IT 由外包服务商运维**。产品的 MSP 多租户 + 客户网点结构,意味着可以卖给"服务商"而非只卖给"甲方"——一个服务商租户管理几十家连锁客户。这是区别于大厂 ITSM 的差异化渠道,蓝图 P4 的 MSP 商业化应以此为锚。

### 5.4 风险提示

- 行业包的最大风险不是功能缺失,而是**模板质量**(SLA 数值、审批层级、CI 分类是否符合行业惯例)。建议每个行业找 1-2 家种子客户共创模板,而不是闭门造车。
- 医疗行业不能以模板包替代合规与安全工程；敏感数据隔离、恢复演练和委派访问验证是试点前置条件。
- 移动端若自研成本高,可评估"飞书/企微应用内嵌 H5"的低成本路径先行验证需求。
