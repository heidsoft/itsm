## CAPABILITY

把「部署能起来、升级不出事、隔离能证明、版本能追溯」从**工程自觉**升级为**产品能力**，使其成为开源转化的第一道信任门槛、企业采购的评审加速器、以及续费与版本渗透的保障机制。

一句话：**可升级性本身就是产品特性，不是运维负担。**

### 1.2 问题聚类：五类结构性缺口

| 聚类 | 问题 | 性质 |
|:---|:---|:---|
| **A. 环境耦合** | 项目名/端口/网络/资源在 dev 与 prod 间无契约 | 设计缺陷（今天已修 A1–A3，但机制未产品化） |
| **B. 升级不可预期** | 迁移顺序契约、checksum 门禁、legacy 重放、索引执行缺口、无 dry-run | **能力缺失（最严重）** |
| **C. 版本不可追溯** | `latest`、无 digest、无发布证据包、无回滚锚点 | 能力缺失 |
| **D. 隔离不可证明** | 缺列/缺索引/RLS 状态散落，无客户可读的证明物 | 能力缺失 |
| **E. 环境不可自愈** | 开发者遇到 buildx/端口/网络问题只能靠口口相传 | 体验缺陷 |

## 二、商业影响升维：每个缺口对应哪一段客户旅程

| 缺口 | 客户旅程节点 | 商业后果 | 受影响指标 |
|:---|:---|:---|:---|
| A 环境耦合 | 私有化 POC 交付 | POC 失败率上升；实施人天不可控 | 开源→POC 转化率、实施毛利 |
| B 升级不可预期 | **版本升级（续费触点）** | 「升级即事故」→ 客户拒绝升级 → 版本渗透停滞、支持成本上升 | 版本升级成功率、续费率、支持工时 |
| B4 索引/性能缺口 | 上线后 1–3 个月 | 性能问题变成口碑问题，且难以归因 | 客户满意度、续费 |
| C 版本不可追溯 | 支持合同 / 合规审计 | 无法承诺 SLA 与变更可控；审计前返工 | 大单签约周期、SOC 2 前置成本 |
| D 隔离不可证明 | 企业安全评审 | 评审卡点直接否决（MSP/SaaS 更严） | 大客单价、销售周期 |
| E 环境不可自愈 | 贡献者 / 内部交付 | 贡献者流失；内部迭代效率损失 | 开源生态增速、交付吞吐 |

**核心判断**：这五类缺口的共同特征是——**它们不增加功能，但决定客户敢不敢把生产交给这套系统**。对一个以「ServiceNow 平替 + 本地化私有部署」为定位的产品，升级安全与隔离证明的商业权重高于任何一个新菜单。

## 三、产品设计改进：五项新能力

> 每项能力都按「产品定义 → 用户故事 → 验收标准 → 打包归属 → 落位版本」描述，可直接进 capability contract。

### C1 · Upgrade Guard（升级安全门禁）— 最高优先

**产品定义**：把升级从「祈祷式操作」变成「有预检、有报告、可回滚、留证据」的标准动作。
- **Pre-upgrade Check**：升级前扫描目标库（schema 漂移、未执行迁移、索引缺口、租户覆盖、磁盘/连接数余量），输出兼容性报告 + 预估耗时 + 阻断项清单。
- **兼容性自愈**：库侧漂移在 ent diff 之前被前置钩子修正（今天的 `prepare*Migration` 即雏形），抽象为「Migration Guard」框架。
- **Dry-run**：迁移在脱敏副本上演练（已有 `cmd/migration-lint` + 脱敏副本 SQL 生成能力可复用）。
- **一键回滚 + 证据包**：升级完成后产出 SHA/digest/迁移结果/耗时/E2E 结论的不可变证据包。

**用户故事**：作为运维负责人，我要在业务窗口前拿到「这次升级能不能过、要多久、最坏怎么退回去」的书面结论，再向上级申请窗口。

**验收标准**：对含数据的历史库，`pre-upgrade check` 能 100% 命中今天 B1/B4 两类问题；升级失败可一键回到升级前镜像 + 库快照，RTO < 10 分钟。

**打包**：社区版给「检查 + 报告」；企业版给「自动编排 + 回滚 + 证据包 + 升级 SLA 承诺」。

---

### C2 · Doctor（部署自诊断）

**产品定义**：一条命令/一个端点回答「我现在这套部署到底健康吗」。
- `itsm-cli doctor` / `GET /api/v1/diagnostics`，覆盖：容器与网络形态、端口冲突、镜像与运行版本一致性、迁移账本与漂移、索引缺口、租户覆盖、outbox 积压与死信、buildx/构建环境。
- 与已有 `GET /api/v1/capabilities`（`deploymentReady`/`degradedReason`）合并为同一事实源，避免第二套健康真相。

**用户故事**：作为刚克隆仓库的开源用户，我要在 5 分钟内知道我的部署是否达标、差在哪，而不是翻日志。

**验收标准**：从 `git clone` 到 doctor 给出全绿报告 ≤ 10 分钟；每一类问题给出可执行修复建议（而非仅报错）。

**打包**：社区版基础自检（引流）；企业版「持续巡检 + 告警 + 多租户巡检报表」。

---

### C3 · Isolation Proof（隔离证明）

**产品定义**：把多租户隔离从「架构承诺」变成「客户评审可读的证据」。
- 租户覆盖矩阵（每表 tenant_id / RLS 策略 / 豁免理由）自动生成；
- 隔离测试套件（跨租户越权用例）可重复执行并输出报告；
- RLS 灰度状态面板（三档就绪度）。

**用户故事**：作为客户安全负责人，我要一份能放进评审材料的隔离证明，而不是听供应商口述。

**验收标准**：`make isolation-report` 输出含覆盖率、越权用例结果、豁免清单（带 ADR 链接）的报告，可直接附入安全评审。

**打包**：社区版给测试套件；企业版给可导出报告 + RLS 灰度工具。

---

### C4 · Release Evidence（版本证据链）

**产品定义**：每个版本都自带不可篡改的「出生证明」。
- 组合要求：不可变 `VERSION`（禁止 `latest` 进生产）+ 镜像 digest + Git SHA + 迁移结果 + E2E 结论 + 恢复演练记录；
- 作为发布门禁**与**商业支持合同的锚点（客户报障时以证据包定位版本状态）。

**用户故事**：作为交付负责人，我要在客户现场 30 秒内证明「跑的是哪个版本、做过哪些验证」。

**验收标准**：`make release-evidence` 一次产出全部字段；缺任一字段则门禁失败（对齐 ROADMAP 未勾选的 2 条发布门禁）。

**打包**：开源项目自身必需（可信度）；企业版附加客户侧升级合规档案。

---

### C5 · Ops Console（运维控制台产品化）

**产品定义**：把散落在 CLI/SQL/日志里的运维动作，收敛为面向角色的控制台。
- 迁移与升级状态、索引与性能基线、outbox 积压/重放/死信、备份与恢复演练、租户级健康度；
- MSP 场景按租户视图售卖（今天已落地的 `TenantHealth` 端点是其最小切片）。

**用户故事**：作为 MSP 运营者，我要在一个看板上管 N 个租户的升级与健康，而不是 N 个终端。

**验收标准**：运维动作 100% 留审计；普通租户不可见其他租户数据。

**打包**：企业版 / MSP 版。

## 四、产品设计原则（建议写入 CONSTRAINTS）

1. **可升级性优先于新功能**：任何变更若使升级需要人工介入，视为设计缺陷，优先修复。
2. **默认可自诊断**：新增能力必须同时提供健康判据与降级原因，否则不予发布。
3. **迁移即代码 + 证据**：迁移必须有顺序契约、可演练、可回滚、有执行登记；「脚本写好未执行」视为事故。
4. **隔离可证明**：涉及租户的数据结构，必须同时产出覆盖率证据与豁免理由。
5. **环境零耦合**：dev / prod / SaaS / MSP 在同一主机或同一集群并行时，不得因命名、端口、网络而互相影响。
6. **版本不可变**：生产环境不允许 `latest` 作为事实版本。

## NON-GOALS

- 不引入第二套健康真相源（Doctor 必须复用 `/api/v1/capabilities`）。
- 不为「看起来很完整」而新增运维 UI；Ops Console 只在有 MSP/多租户真实需求后立项。
- 不把升级安全做成阻断式强制门禁（社区版必须可跳过，企业版才提供强制与承诺）。
