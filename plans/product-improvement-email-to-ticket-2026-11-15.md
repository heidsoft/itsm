# ITSM Email-to-Ticket 产品就绪度改进方案

> 视角：产品专家（商业化 / GTM 就绪度）
> 依据：本地 prod 商业化场景端到端验证（2026-11-14 实测，2026-11-15 复盘）
> 关联：工程侧见 `plans/optimized-improvement-plan-2026-11-14.md` 的 W0 旗舰项；战略见《CloudMesh 商业化战略与开源运营指导手册 V1.0》§3.3 / §9

## 0. 一句话结论

技术闭环**已验证可用**：`POST /email-intake/conversations/{id}/confirm` 能稳定产出 `INC-xxxx` 事件、关联客户与合同、置信度可回溯（浏览器 + API + DB 三重证据）。

但**产品开箱即用的"可收费闭环"尚未成立**——它依赖工程手工注入 `EMAIL_INTAKE_AUTOMATION_REPORTER_ID` 配置 + 手工 SQL 种子数据才能跑通演示。这不是技术缺陷，而是**产品化 / 上市（GTM）就绪度缺口**：

> 当前状态 = "需手术刀才能演示"，目标状态 = "一条命令可演示 / 开箱即见价值"。

## 1. 测试暴露的 4 个断点（技术事实 → 产品后果）

| 断点 | 技术事实（实测） | 产品后果 |
|---|---|---|
| **配置断点** | prod 未设 `EMAIL_INTAKE_AUTOMATION_REPORTER_ID`，确认→建单链路默认关闭 | 客户/销售点击确认"毫无反应"，误判功能坏了 |
| **数据断点** | prod 无任何邮件报障演示数据、无 IMAP 入站邮箱配置 | 进入 email-intake 是空 NOC 队列，零"哇点"可展示 |
| **认知断点** | `EMAIL_INTAKE_MODE` 无默认且整库无文档 | 用户不知道现在是"观察"还是"自动"，信任受损 |
| **体验断点** | 工作台无引导 / 无示例 / 无模式状态提示 | 新手 30 秒流失，无法感知价值 |

## 2. 改进方案（按 GTM 阻断度排序）

### P0 — 阻断对外演示与试用（必须做）

1. **零代码"演示模式"开关包**
   - 在 `.env.example` + 部署文档补齐三件套：`EMAIL_INTAKE_AUTOMATION_REPORTER_ID` / `EMAIL_INTAKE_MODE` / IMAP 变量。
   - 提供 `MODE=demo` 一键组合（compose 内 `profiles` 或 env 模板），杜绝每次手工写 `docker-compose.emailtest.yml` 覆盖文件。

2. **默认行为文档化（消除认知断点）**
   - 明确写出："当前默认 = 人工确认（观察）模式，不自动建单；设 reporter id 后进入半自动"。
   - 在 email-intake 页面用**实时状态徽标**显示当前模式（观察 / 半自动 / 自动），把"看不见变化"变成"明确知道在做什么"。

3. **一次性脱敏种子脚本 `scripts/seed-email-intake-demo`**
   - 建脱敏客户（示例科技有限公司）/ 合同（SUP-2026-001）/ 合成会话（置信 0.92），让销售 / DevRel 一条命令复现 `INC-xxxx` 闭环。
   - 附带 `unseed` 一键清理：**复用本次已验证的 FK 安全删除序**（incident+7 子表 → 入站/出站邮件 → 会话 → external_contract_references → 合同 → customer_branches → 客户），原子回滚零残留。

### P1 — 产品体验（决定转化）

4. **Email-intake 工作台空态设计**
   - 引导文案 + "加载示例数据"按钮 + 模式状态徽标；首屏即告知价值，不靠工程师口头解释。

5. **闭环可观测性回执**
   - 确认后给出"已建单 `INC-XXXX`"回执 + 跳转事件详情，强化价值感知，而非静默成功。

6. **隔离演示租户**
   - 预置一个隔离 demo tenant 自带脱敏数据，对外演示不污染生产租户（呼应既有多租户隔离架构）。

### P2 — 商业化包装（决定收费）

7. **定位落地证明**
   - 把 Email-to-Ticket 作为手册 §3.3 / §9"首个可收费闭环"的**可用证明**，配套 ROI 叙事（自动处理占 L1 工单 X% → 省 Y 人力）。

8. **计量钩子设计（规划态）**
   - 按"自动建单量 / 处理邮件量"设计收费计量，与手册对齐；**仅规划，未实装**。

9. **对标话术（口径严守）**
   - 对比 ServiceNow Email-to-Case 的差异化（开源可自托管、数据不出域）；**不宣称替代**，标注为 Preview。

- **不宣称 GA**：Email-to-Ticket 标注 Preview，prod 默认观察模式。
- **演示数据必须脱敏且可一键清理**（本次清理已证明可原子回滚，无残留）。
- **计量 / 收费仅为产品规划，未实装**，不对用户承诺 SLA。
- 协议 **Apache-2.0** 不变；**不写"替代 ServiceNow"**。
- 验证期间产生的临时覆盖文件与种子数据，**已全部还原 / 清除**，prod 当前为原始配置态。
